# Food Event Ingestion Service

An asyncio gRPC service that receives analytics events from a food-ordering platform, micro-batches them, and writes each batch to Kafka as **one transaction** using idempotent, transactional producers. It adds exponential retry with full jitter, isolation of poison records, and a dead-letter queue (DLQ). A realistic load generator and a `read_committed` verifier exercise it end to end.

- **Python 3.11+**, `grpc.aio`, `aiokafka`, Protobuf (the same messages are used on the wire and as the Kafka value), Redis dedupe, `pydantic-settings`, `structlog` JSON logs, Prometheus metrics.
- An **ACK means committed.** A client only gets `ACCEPTED` after the Kafka transaction containing that event has committed.

---

## Architecture

```
 client ──gRPC──▶ RequestLoggingInterceptor ─▶ AuthInterceptor (API key → tenant_id)
                                                   │
                                                   ▼
                                         IngestionServicer  (thin orchestration)
   1 stamp tenant_id + received_time ───────┤
   2 EventValidator ──invalid──▶ REJECTED_INVALID ──▶ DlqPublisher ──▶ food.events.dlq
   3 RedisEventDeduplicator.reserve (SET NX "pending") ──seen──▶ DUPLICATE
   4 PendingEvent(envelope, record, Future) ─▶ EventBatchAccumulator (bounded queue)
   5 await futures (request timeout) ◀───────────────┐            │ flush on 500 recs /
                                                     │            │ 1 MiB / 100 ms
                                                     │            ▼
                                                     │   TransactionalPublisher
                                                     │     lease producer from TransactionalProducerPool (N tx ids)
                                                     │     begin → send all → await sends → commit
                                                     │     ├ ok: dedupe "committed" → resolve ACCEPTED
                                                     │     ├ RETRIABLE: abort → backoff+jitter → retry whole batch
                                                     │     ├ FATAL: discard producer → recreate (same tx id, fences epoch) → retry
                                                     │     ├ NON_RETRIABLE: bisect → only poison records → DLQ
                                                     └─────┴ exhausted: DLQ all → SENT_TO_DLQ (or FAILED) → release dedupe
```

| Package | Responsibility |
|---|---|
| `ingestion/config.py` | Typed settings (`INGEST_*` env / `.env`) |
| `ingestion/main.py` | Composition root: wires everything by constructor injection, handles SIGTERM |
| `ingestion/api/` | gRPC server, interceptors (auth, logging/timing), servicer |
| `ingestion/domain/` | `models.py`, `validation.py`, `routing.py` (the single routing registry), `protocols.py` (Protocols for fakes) |
| `ingestion/batching/` | `EventBatchAccumulator`: bounded queue, size/bytes/time flush, backpressure |
| `ingestion/kafka/` | producer factory, pool, transactional publisher, DLQ publisher, serializers, error classifier, connection/security options |
| `ingestion/resilience/` | `ExponentialBackoffPolicy` (full jitter) |
| `ingestion/dedupe/` | Two-phase Redis deduplicator |
| `ingestion/observability/` | structlog setup, Prometheus metrics (injected registry, no globals) |
| `ingestion/generated/` | Protobuf/gRPC stubs, **generated by `make proto`; never edit** |

### Topics and routing

All routing lives in [`ingestion/domain/routing.py`](src/ingestion/domain/routing.py) (`ROUTING_REGISTRY`). Adding an event type takes a proto change plus **one registry entry**. `scripts/create_topics.py` reads the same module.

| Topic | Partitions | Event types | Partition key |
|---|---|---|---|
| `food.orders.v1` | 12 | `order_placed` | `{tenant_id}:{order_id}` |
| `food.feedback.v1` | 6 | `rating_prompt_shown`, `rating_submitted` | `{tenant_id}:{order_id}` |
| `food.browse.v1` | 24 | `item_viewed`, `price_filter_applied`, `cart_item_added` | `{tenant_id}:{session_id}` |
| `food.sessions.v1` | 12 | `session_started` | `{tenant_id}:{user_id}` |
| `food.events.dlq` | 6 | anything that permanently failed (`DlqRecord`) | `{tenant_id}:{event_id}` |

Keys are never the tenant alone (to avoid hot partitions). Every record carries the headers `event_type`, `schema_version`, `tenant_id`, `event_id`, `producer_id`. DLQ records also carry `error_class` and `failed_stage`.

### Contract

The protos live in [`proto/events/v1/`](proto/events/v1). The schema-evolution rules are at the top of `events.proto`: add fields only, never reuse or renumber (use `reserved`), and breaking changes go to `events.v2` and a new topic.

## Running it

Prerequisites: Docker, and [uv](https://docs.astral.sh/uv/) (or Python 3.11+ with pip).

```bash
make install      # venv + editable install with dev extras
make proto        # generate stubs into src/ingestion/generated/
make up           # Kafka (KRaft, single broker), Redis, kafka-ui on http://localhost:8080
make topics       # idempotent: existing topics are skipped
make run          # start the service on :50051 (metrics on :9100/metrics)
```

In a second terminal:

```bash
make generate                                     # 200 ev/s for 30 s, 50 events per request
make generate GENERATOR_ARGS="--rate 1000 --duration 60 --batch-size 100 \
  --late-ratio 0.05 --invalid-ratio 0.03 --duplicate-ratio 0.05 --seed 7"
make verify                                       # read_committed check against generator_report.json
```

Example `make generate` summary:

```
status counts:
  ACCEPTED         : 7375
  DUPLICATE        : 360
  REJECTED_INVALID : 265
  SENT_TO_DLQ      : 0
  FAILED           : 0
ack latency ms       : p50=134.9 p95=140.7 p99=142.6
```

`make verify` then checks that no `event_id` was committed twice and that the committed events exactly match those the clients were told were accepted. It also prints a DLQ breakdown by `error_class`.

Other targets: `make test` (unit + integration), `make test-unit`, `make test-integration`, `make lint` (ruff + `mypy --strict`), `make format`, `make down` (also removes volumes).

### Dummy data generator

`scripts/generate_dummy_events.py` generates realistic data:
- **Catalog:** 5 tenants, 50 restaurants, and 80 dishes across biryani, dosa, thali, pizza, burger, chinese, desserts and beverages, priced ₹60–₹900.
- **Timing:** journeys peak at lunch (12:30–14:30) and dinner (19:30–22:30) IST.
- **Ratings:** skewed toward 4–5 stars.
- **Popularity:** dish and restaurant popularity follow a Zipf distribution.
- **Journeys:** `session_started → item_viewed → price_filter_applied → cart_item_added → order_placed → rating_prompt_shown → rating_submitted`, with consistent `session_id`/`order_id` and realistic drop-off.

Fault-injection flags:

| Flag | Effect |
|---|---|
| `--late-ratio` | `event_time` shifted 1–3 days back. These are still valid and get ACCEPTED. |
| `--invalid-ratio` | `rating=7`, a negative price, or a missing identity → `REJECTED_INVALID` plus a DLQ record. The server always derives `tenant_id` from the API key, so a *missing client tenant* alone is not an error. The generator clears the tenant together with the identity fields the tenant-scoped key needs. |
| `--duplicate-ratio` | Re-sends events with the same `event_id` → `DUPLICATE` |

Like a well-behaved client, the generator also re-sends `FAILED` events with the same `event_id` until they resolve.

## Idempotency and delivery guarantees

Four layers cooperate. Each covers a different failure.

1. **Producer idempotence covers internal retries.** With `enable_idempotence=True` and `acks=all`, the broker deduplicates a producer's own retried sends by producer id, epoch and sequence number. Network blips and broker failovers don't create duplicates.
2. **Transactions give atomic multi-topic batches.** A flushed batch can span several topics and is one Kafka transaction: either every record in it becomes visible, or none does. On failure the transaction is aborted and the **same event_ids** are retried. Aborted records stay physically in the log but are invisible to `read_committed` readers. The integration tests assert both halves: 1 copy under `read_committed` and 3 under `read_uncommitted` after two aborted attempts. Each pooled producer has a stable `transactional_id`. Recreating one (after a FATAL error, or after a restart) bumps the epoch and fences any zombie still holding the old one.
3. **Redis dedupe covers client-level resends.** Using `SET dedupe:{tenant}:{event_id} "pending" NX EX 300`, only one request can publish a given event. The marker becomes `"committed"` (7-day TTL) only **after** the Kafka commit. On failure it's released by a compare-and-delete Lua script, so a failed batch can never erase a committed marker, and the client can safely retry. A resend of a committed event gets `DUPLICATE`.
4. **Downstream consumers MUST use `isolation_level=read_committed`.** Otherwise they will see records from aborted transactions, including every retried attempt.

**Edge cases handled explicitly:**
- **Ack timeout** (Kafka slower than `INGEST_GRPC__REQUEST_TIMEOUT_MS`). The client gets `FAILED` ("outcome pending"), but the batch keeps going. A resend returns `DUPLICATE` if it committed meanwhile. The generator does this, and `make verify` counts these events as confirmed.
- **Ambiguous commit** (`commit_transaction` itself times out). The outcome is unknown, so the batch is **neither retried nor dead-lettered**: retrying could duplicate it, and dead-lettering could lose it. The events get `FAILED` and their pending markers are left to expire. This leaves a small window: if that commit *did* land and the client resends after the pending TTL, a duplicate is possible. Consumers that need strict exactly-once should also dedupe on the `event_id` header.
- **Redis unavailable.** The service fails closed: events get `FAILED` ("retry later") and are never published without a reservation.
- **Ordering.** Order is preserved within a batch per partition key. With `PRODUCER_POOL_SIZE > 1`, two batches can commit out of order, so consumers should order by `event_time`. Set the pool size to 1 for strict per-key order.

### Failure handling

| Error class | Examples | Handling |
|---|---|---|
| RETRIABLE | `KafkaTimeoutError`, `NotEnoughReplicasError`, `LeaderNotAvailableError`, `RequestTimedOutError`, `KafkaConnectionError`, coordinator errors, send-phase timeout | abort, then retry the whole batch with full jitter: `uniform(0, min(5 s, 100 ms·2^attempt))`, up to 5 attempts |
| NON_RETRIABLE | `MessageSizeTooLargeError`, `RecordTooLargeError`, `InvalidTopicError`, serialization errors | no retry; **bisect** the batch so only the poison records go to the DLQ and the rest commit |
| FATAL | `ProducerFenced`, `OutOfOrderSequenceNumber`, `InvalidProducerEpoch`, `UnknownProducerId`, invalid txn state | close the producer, recreate it with the same `transactional_id` (re-init transactions), then retry |
| exhausted | any of the above after max attempts | every event goes to the DLQ → `SENT_TO_DLQ`, pending markers are released. If the DLQ write also fails after its own retries: `FAILED`, an ERROR log and `ingestion_dlq_write_failures_total`. Nothing is dropped silently. |

The DLQ uses a **separate idempotent, non-transactional producer**, so a wedged transactional producer can't block dead-lettering. `DlqRecord` contains the original topic, the original payload bytes, the ids, the error class and message, the failed stage (`VALIDATION`, `SERIALIZATION` or `PUBLISH`), the attempt count, and first/last failure timestamps.

### Shutdown (SIGTERM)

Shutdown runs in this order:
1. The accumulator stops accepting; new requests get `UNAVAILABLE`.
2. The gRPC server stops taking RPCs and gives in-flight ones the grace period.
3. Every queued event is flushed and committed, or dead-lettered.
4. Background DLQ writes are drained.
5. The producers, DLQ producer and Redis connection are closed.

### Backpressure

The accumulator queue is bounded. A request is enqueued all-or-nothing, and when the queue is full the request fails with `RESOURCE_EXHAUSTED` (reservations are released, so a retry is safe). At most `MAX_IN_FLIGHT_BATCHES` transactions are in flight at once.

## Tests

```bash
make test-unit          # no infrastructure needed (fakes + fakeredis)
make up && make topics  # then:
make test-integration   # real Kafka + Redis
IT_CHAOS=1 .venv/bin/python -m pytest tests/integration -k real_broker   # pauses the kafka container
```

- **Unit tests:** backoff bounds and jitter; the error-classifier mapping; accumulator flush on records, bytes and time, plus backpressure and drain; routing of every event type and key; validator rules; two-phase dedupe with fakeredis. Publisher tests cover retry, bisection, the FATAL recreate, the DLQ fallbacks and ambiguous commits. Servicer tests run over a real in-process gRPC server and cover auth, tenant overwrite, duplicates, backpressure, and ack timeouts.
- **Integration tests:**
  - a happy-path multi-topic batch with key and header checks
  - duplicate submission returns `DUPLICATE`
  - a broker failure mid-batch: real records are written, the commit fails, then abort and retry give exactly-once
  - a persistent failure sends the batch to the DLQ, then succeeds on resend
  - invalid event → DLQ
  - an aborted transaction is invisible to `read_committed`
  - opt-in: a real broker pause mid-batch

### Manual chaos check

```bash
make run &   # terminal 1
(sleep 6; docker pause ingestion-kafka; sleep 40; docker unpause ingestion-kafka) &
make generate GENERATOR_ARGS="--rate 200 --duration 75 --seed 13" && make verify
```

Expected result: requests stall and some get `FAILED` on the ack timeout. The producers are discarded and recreated, the batches commit after the unpause, and the resent events come back `DUPLICATE`. `make verify` reports no duplicates, committed == acknowledged.
